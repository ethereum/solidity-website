We are excited to announce the release of the Solidity Compiler [v0.8.35](https://github.com/argotorg/solidity/releases/tag/v0.8.35)!

This release introduces our first compile-time builtin, [`erc7201`](#erc7201-compile-time-builtin), which computes the base slot of an ERC-7201 namespaced storage layout from its namespace string.
It also formalizes how experimental features are exposed to users: in-development functionality is now gated behind a new top-level `--experimental` flag, with [a documented lifecycle and a canonical list](https://docs.soliditylang.org/en/v0.8.35/using-the-compiler.html#experimental-mode) of which features are currently considered experimental.
The first major code-generation feature shipped under this new lifecycle is an experimental SSA-form control-flow graph (SSA CFG) code generator that we expect to be the long-term answer to stack-too-deep errors in the IR pipeline.
We are also reorganizing the `ethdebug` outputs to match our usual conventions and decoupling them from binary compilation.

It also continues the [0.9.0 deprecation work started in 0.8.31](https://soliditylang.org/blog/2025/12/03/solidity-0.8.31-release-announcement/#feature-deprecations), this time warning about identifiers that will be promoted to keywords in 0.9.0.

Some of these features were previously available in the [v0.8.35-pre.1 pre-release](https://github.com/argotorg/solidity/releases/tag/v0.8.35-pre.1) we shared back in March.

## Notable Features and Changes

### `erc7201` Compile-Time Builtin

Solidity 0.8.35 introduces a new builtin function:

```solidity
function erc7201(string memory id) returns (uint)
```

It computes the base storage slot for a namespace string using the formula defined in [ERC-7201](https://eips.ethereum.org/EIPS/eip-7201), equivalent to `keccak256(keccak256(id) - 1) & ~0xff`.
ERC-7201 formalizes the practice of placing a contract's state behind a hashed namespace to avoid storage collisions in proxy-based and diamond-style upgradeable patterns.

The builtin pairs naturally with the [`layout at` storage layout specifier](https://docs.soliditylang.org/en/v0.8.35/contracts.html#custom-storage-layout) introduced in 0.8.29 and extended in 0.8.31:

```solidity
contract MyContract layout at erc7201("openzeppelin.storage.MyContract") {
    uint256 x;
    uint256 y;
}
```

What makes `erc7201` special is that **it is the first compile-time builtin in the language**.
Until now, Solidity's compile-time evaluator only handled arithmetic on rational number literals; existing builtins like `keccak256` are not constant-foldable.
`erc7201` is the first whose result can be used wherever a constant expression is required: as the base slot in `layout at`, as an array length, in a `uint constant` initializer, and so on.
This directly addresses one of the limitations we [flagged in 0.8.31](https://soliditylang.org/blog/2025/12/03/solidity-0.8.31-release-announcement/#constants-in-storage-layout-specifiers), and we expect more such builtins as we work toward a more capable compile-time evaluator.

### Formalizing the Experimental Feature Process

Past releases have shipped a number of in-development features through a mix of ad-hoc CLI flags and `pragma experimental` directives.
There was no consistent way for a user to know they were opting into something unstable, and the metadata signaling was patchy.

With 0.8.35 we are formalizing this.
The full process is described in the new [Experimental Mode docs page](https://docs.soliditylang.org/en/v0.8.35/using-the-compiler.html#experimental-mode); the key user-facing changes are below.

#### The `--experimental` Flag

Using any experimental feature now requires the new top-level `--experimental` flag, or the analogous boolean `settings.experimental` field in Standard JSON input.
`--experimental` is a master toggle: it does not enable any specific feature on its own, but is required for any of the per-feature flags or pragmas to be accepted.
The current list of experimental features, their IDs and the flags or pragmas that drive each one is maintained in the [Experimental Mode docs page](https://docs.soliditylang.org/en/v0.8.35/using-the-compiler.html#experimental-mode).

Using any of those without `--experimental` is now a hard error.
This is a backwards-incompatible change for users who were already passing the affected flags directly: they will need to add `--experimental` (or set `settings.experimental: true` in JSON input) to keep their builds working.
We think the explicit opt-in is worth the migration cost: experimental features come with **no backwards-compatibility guarantees and may change in breaking ways even in non-breaking releases**, and we want users to be making that tradeoff knowingly.

#### Recorded in Metadata

Whether a contract was compiled with experimental mode enabled is now recorded in both JSON and CBOR metadata.
The CBOR `experimental` field, which previously only signalled experimental pragmas in the source, has been broadened to cover this.
This also closes a known gap: targeting an unreleased EVM version used to produce experimental bytecode without flipping the flag.

#### Experimental `@future` EVM Version

This release also introduces a new EVM version selector, `@future`, that sits one slot above the current default (`osaka`).
As of 0.8.35 it does not gate any new functionality compared to `osaka`, but it gives us a stable target to land EVM features that are still in flux at the protocol level (e.g. opcodes from upcoming hardforks) before committing to a named version.
Selecting it via `--evm-version @future` requires `--experimental`, and doing so sets the `experimental` flag in metadata.

### Experimental SSA CFG Code Generator

The first major code-generation feature shipped under the new experimental lifecycle is an SSA-form control-flow graph (SSA CFG) code generator: a new EVM backend in the IR pipeline that produces bytecode by walking a static-single-assignment representation of each basic block, using a precomputed stack layout, and shuffling the EVM stack to match.

Why we are building it: stack-too-deep has been a long-standing pain point in Solidity, hitting users on both the legacy and IR pipelines.
In our [2025 Developer Survey](https://soliditylang.org/survey-2025/), it [remained the most commonly reported recurring issue](https://soliditylang.org/blog/2026/04/15/solidity-developer-survey-2025-results/#pain-points).
The current Yul-to-EVM code transform that drives the IR pipeline relies on heuristics that struggle with deeply nested expressions and complex control flow, and an SSA-based backend gives us a much stronger foundation for stack scheduling and optimization.
We see it as the realistic long-term path to making stack-too-deep a non-issue in the IR pipeline.

Enable it with `--experimental --via-ssa-cfg` on the command line, or `settings.experimental: true` together with `settings.viaSSACFG: true` in Standard JSON.
Both imply `--via-ir`.

The implementation is still maturing. Two limitations to be aware of:

- The codegen is exercised against the full external-contract semantic test suite on every PR, but it is not yet the default for `--via-ir`. We want to gather gas data on real contracts before promoting it.
- Cases that exhaust the stack scheduler still surface as internal compiler errors rather than graceful "stack too deep" diagnostics.

We expect both to be addressed over the coming releases.
Per the new experimental policy, only major changes affecting it will be recorded in the changelog.

### More Granular `ethdebug` Output Selection

The previous `--ethdebug` and `--ethdebug-runtime` CLI flags have been replaced with four more granular flags, each mapping directly onto a part of the [ethdebug spec](https://github.com/ethdebug/format):

- `--ethdebug-resources`: the `ethdebug/format/info/resources` schema (requires only analysis).
- `--ethdebug-compilation`: the `compilation` key from the same schema (no compilation needed).
- `--ethdebug-program`: per-contract `ethdebug/format/program` for the creation bytecode.
- `--ethdebug-program-runtime`: same, for the deployed bytecode.

The Standard JSON ethdebug output has been reorganized along the same lines: the previous top-level `ethdebug` key has been split into `ethdebug.resources` and `ethdebug.compilation`, and per-contract program outputs are now selected via the standard `evm.bytecode.ethdebug` and `evm.deployedBytecode.ethdebug` keys instead of being lumped under a separate top-level blob.

The main user-visible improvement: ethdebug outputs no longer force a full binary compilation.
Previously, requesting any ethdebug data would trigger bytecode generation even when bytecode was not in the output selection; each output now declares only the pipeline stages it actually needs.

ethdebug remains experimental and now requires `--experimental` like the others.

### Deprecation Warnings for Upcoming 0.9.0 Keywords

Continuing the [deprecation work started in 0.8.31](https://soliditylang.org/blog/2025/12/03/solidity-0.8.31-release-announcement/#feature-deprecations), this release adds warnings for identifiers we plan to promote to keywords in 0.9.0.
Where 0.8.31's deprecations were about features being removed, this batch is about names being claimed.

Solidity declarations using `at`, `error`, `layout`, `super`, `this`, or `transient` will now emit a warning.
In Yul (standalone or inline assembly), `leave` will become a Yul keyword, while `basefee`, `blobbasefee`, `blobhash`, `clz`, `mcopy`, `memoryguard`, `prevrandao`, `tload`, and `tstore` will become Yul reserved identifiers, cleaning up the per-EVM-version exceptions list that has accumulated as new opcodes were introduced.

These are warnings, not errors. Existing code continues to compile; you have a window to rename affected declarations before 0.9.0 turns the warnings into errors.

### `--revert-strings strip` Preserves Custom Errors

`--revert-strings strip` (or `revertStrings: "strip"` in Standard JSON) is meant to strip user-supplied revert reason strings from compiled bytecode.
In the IR pipeline (`--via-ir`), it was also stripping the custom-error argument of [`require(condition, CustomError(...))`](https://soliditylang.org/blog/2024/05/21/solidity-0.8.26-release-announcement/#requires-with-custom-errors), so a failed `require` reverted with empty error data instead of the encoded custom error.
The legacy pipeline was unaffected.

The bug has been present since `require(bool, error)` was introduced in 0.8.26 and is fixed in 0.8.35.
The documentation and `--help` output for `--revert-strings` have also been clarified to state explicitly that `strip` does not remove custom errors.

## Full Changelog

### Language Features
* General: Add a builtin that computes the base slot of a storage namespace using the `erc7201` formula from ERC-7201.
* NameAndTypeResolver: Warn about identifiers selected for future promotion to Solidity keywords.
* Yul Analyzer: Warn about identifiers selected for future promotion to Yul keywords.

### Compiler Features
* Commandline Interface: Disallow selecting the deprecated assembly input mode that was only accessible via `--assemble` instead of treating it as equivalent to `--strict-assembly`.
* Commandline Interface: Introduce `--experimental` flag required for enabling the experimental mode.
* Commandline Interface: Replace `--ethdebug` and `--ethdebug-runtime` with more granular `--ethdebug-resources`, `--ethdebug-compilation`, `--ethdebug-program` and `--ethdebug-program-runtime` flags. Per-contract program outputs no longer force full binary compilation.
* EVM: Introduce experimental EVM version `@future`.
* General: Improve performance of sanity checks throughout the compiler implementation.
* General: Introduce the SSA CFG codegen (experimental).
* General: Restrict the existing experimental features (`generic-solidity`, `lsp`, `ethdebug`, `eof`, `evm`, `ast-import`, `evmasm-import`, `ir-ast`, `ssa-cfg`) to experimental mode.
* Metadata: Store the state of the experimental mode in JSON and CBOR metadata. In CBOR this broadens the meaning of the existing `experimental` field, which used to indicate only the presence of certain experimental pragmas in the source.
* Standard JSON Interface: Introduce `settings.experimental` setting required for enabling the experimental mode.
* Standard JSON Interface: Replace the top-level `ethdebug` output with `ethdebug.resources` and `ethdebug.compilation`. Decouple ethdebug outputs from binary compilation so that global ethdebug outputs can be produced without generating bytecode.
* Yul Optimizer: Improve performance of control flow side effects collector and function references resolver.

### Bugfixes
* Yul: Fix incorrect serialization of Yul object names containing double quotes and escape sequences, producing output that could not be parsed as valid Yul.
* Yul EVM Code Transform: Improve stack shuffler performance by fixing a BFS deduplication issue.
* Yul IR Code Generation: Preserve custom error argument of `require` when stripping of revert strings is selected via `--revert-strings strip`.

## How to Install/Upgrade?

To upgrade to the new version of the Solidity Compiler, please follow the [installation instructions](https://docs.soliditylang.org/en/v0.8.35/installing-solidity.html) available in our documentation.
You can download the release from GitHub: [v0.8.35](https://github.com/argotorg/solidity/releases/tag/v0.8.35).

If you want to build from the source code, do not use the source archives generated automatically by GitHub.
Instead, use the [`solidity_0.8.35.tar.gz` source tarball](https://github.com/argotorg/solidity/releases/download/v0.8.35/solidity_0.8.35.tar.gz) or check out the `v0.8.35` tag via git.

And last but not least, we would like to give a big thank you to all the contributors who helped make this release possible!
